# 给 agent 的读取说明

> 本文件是同一份 PRD 的机器可读版本。构建任何模块前，先读本节，再按下面的优先级取用。

**冲突时的优先级（高 → 低）**

1. 标了 `P0` 的条目与 `R-xx` 需求条目（第 6 章）
2. 第 5.3 节的速度/权重公式与表（唯一权威，其它章节的数字都由它推导）
3. 附录 A 的状态机矩阵与进入条件（状态流转以矩阵为准，文字描述仅作解释）
4. 其余描述性文字

**必须先读的四段**

| 顺序 | 章节 | 为什么 |
| --- | --- | --- |
| 1 | §2 目标与非目标 | 决定什么不做，避免实现越界功能 |
| 2 | §5.3 难度模型 | 所有速度/权重的唯一来源 |
| 3 | 附录 A 状态机 | 输入与状态的合法组合，写错就是手感 bug |
| 4 | 附录 C 验收清单 | 交付前必须逐条通过 |

**术语速查**：`地块(Block)` 关卡最小单元；`安全轨道` 该地块上不会出现障碍的轨道；`无解率` 在 §9.3 完美玩家模型下所有策略都无法通过的组合占比。

**硬约束（任何实现都不得违反）**

- 三轨，只允许相邻换道，禁止 1 ↔ 3 直跳
- 主状态互斥；空中禁止跳跃/滑铲；换道期间锁全部输入
- 任意地块不得三轨全封；不得连续两块双轨障碍
- 新手保护区（前 3 块地）：无双轨障碍，每块 ≥ 2 条安全轨，第 1 块纯金币
- 手感参数 100% 在 `GameConfig`，改数值不改代码
- 存档原子写入，损坏时降级为默认存档而不是崩溃

**关键参数（机器可读，均取自正文，未额外发明）**

```yaml
lanes: 3
speed_ms:
  v0: 12.0          # §5.3 起始速度
  v_max: 26.0       # §5.3 渐近上限，不是硬阈值
  lambda: 600       # §5.3 距离衰减常数（米）
timing_ms:
  lane_switch: 120  # GameConfig.LaneSwitchDuration
  hit_stun: 300     # GameConfig.HitStunDuration
  judge_window: 120 # 跳跃/滑铲判定窗口，±120ms
  reaction: 250     # §9.3 完美玩家反应时间
  frame: 16.7       # §9.3 决策粒度
vision_m: 40        # §9.3 完美玩家前方视野
newbie_protection_blocks: 3   # 前 3 块地：无双轨、每块 >=2 安全轨
cap_lane_double_weight: 0.30  # §5.3 双轨障碍权重封顶
```

## 0　一页纸

给只有三分钟、只有一只手的人，一个跑得爽、死得明白、重开只要三秒的三轨跑酷。

#### 要解决的问题

跑酷的爽感由三件事决定：读得懂、动得快、死得服。市面上大量小体量跑酷 Demo 恰恰在这三点上失守——无解障碍让人死得不明不白，输入吞键让人怀疑自己的手，存档丢失让人白玩。玩家不是被难度劝退，而是被“不公平感”劝退。V1.1 已经把这四类问题列为发布阻断项，说明这是工程债，不是内容债。

#### V1 的方案

| 层面 | 做法 | 为什么这样 |
| --- | --- | --- |
| 输入 | 三轨五指令，统一输入层，指令冷却锁 | 把复杂度放在系统里，不放在玩家脑子里 |
| 角色 | 主状态严格互斥（跑/跳/落/滑/换道/受击/死） | 消灭“空中二段跳”“滑铲起跳”这类手感冲突 |
| 关卡 | 确定性生成 + 合法性校验 + 离线无解率验证 | 公平不是靠运气，是靠验证 |
| 难度 | 速度按距离平滑逼近硬上限，地块权重同步偏移 | 可预期的变难，而不是突然变难 |
| 存档 | 本地 Json 原子写入 + 损坏降级 | 进度可信是一切留存的前提 |

#### 不做什么（V1 明确排除）

联网、排行榜、社交、内购、广告、二段跳、翻滚、弯道/斜坡/隧道、签到任务、多人对战、云存档。

#### 成功的定义

| 指标 | 目标 | 口径 |
| --- | --- | --- |
| 首局 60 秒完成率 | ≥ 70% | 首次进入游戏、无教程情况下能活过 60 秒 |
| 平均单局时长 | ≥ 90 秒 | 本地埋点，按会话聚合 |
| 次日回访 | ≥ 25% | 本地记录，去重 |
| 死亡后重开率 | ≥ 60% | 结算页点击“再来一局”/ 总死亡次数 |
| 崩溃率 | < 0.5% | 会话级 |
| 1500m 掉帧 | ≤ 10% | 相对开局 30 秒的均值帧率 |

#### 节奏

M0 手感原型 2 周 → M1 可玩闭环 4 周 → M2 打磨 3 周 → M3 发布 1 周。合计 10 周，单人。

#### 最大的两个风险

① 单人排期撑不住功能清单；② 交付包里混入未授权素材（音乐、贴图），到发布前才发现。前者靠“砍范围清单”兜底，后者靠“交付物只放免版权素材 + LICENSES.md 逐项登记”。

## 1　背景与问题定义

### 1.1　问题不是“缺一个跑酷”

跑酷是成熟品类，玩家不需要被教育。真正的缺口是“小而稳”：大厂往内容量上堆，小团队往素材上堆，很少有人把确定性做扎实。玩家离开的原因通常不是“不够好玩”，而是下面三种具体挫败：

| 挫败 | 玩家原话（想象） | 根因 | 我们的对策 |
| --- | --- | --- | --- |
| 死得不明不白 | “这根本过不去吧？” | 无解布局 / 障碍被遮挡 / 视觉误导 | 预制体层面禁止三轨障碍；生成后二次校验 |
| 手不跟手 | “我明明按了！” | 输入延迟 / 状态冲突 / 连按抖动 | 统一输入层 + 严格状态机 + 换道冷却 |
| 进度不可信 | “我的分没了？” | 存档非原子写入 / 异常未兜底 | 原子写 + 损坏降级 + 结算即存 |

这三条来自 V1.1 的问题清单（无解障碍、手感冲突、内存泄漏、存档丢失），它们指向同一个判断：本项目的胜负手在工程确定性，不在美术量。

### 1.2　为什么现在做

- 品类认知成熟，玩家零学习成本，适合作为第一个完整交付的单机项目。
- 单人 + 无服务器 + 无内购，范围可控，10 周内能形成闭环。
- 已有三维/程序化的工程积累（见 1.3），缺的是美术与音频产能——这决定范围必须按“程序化 + 免费素材”来砍。

### 1.3　为什么是你：现有资产盘点

| 资产 | 现状 | 对本项目的作用 |
| --- | --- | --- |
| github.com/Gubao-tian | 公开主页、自动生成的 README、2 个仓库 | 工程可信度；项目门面；招聘方可直接验证 |
| forbidden-city-3d | three.js / MIT / 程序化几何 / 昼夜光照 | 证明“不靠美术也能出画面”；Web 试玩版的技术底子 |
| Python + LLM 应用 | 学习主线 | 离线关卡验证、难度调参、自动化回归 |
| Unity 经验 | 无公开项目 | 最大不确定性：M0 原型必须验证“做得动” |
| 美术 / 音频产能 | 无 | 范围约束：程序化 + CC0 素材，绝不外包 |

结论：你的瓶颈是产能，不是能力。所以本 PRD 的每一个“不做”，都是在保护交付；每一个“做”，都必须能用程序或免费素材落地。

### 1.4　我们要赢在哪

不比内容量，比“每一局都公平可解释”。具体表现为三件事：开局 3 秒内进入游戏、死亡后 1 屏内告诉你为什么死、任何一次死亡都能复盘到具体的输入与地块。

## 2　目标与非目标

### 2.1　目标（OKR 形式，可验收）

| 目标 | 关键结果 | 验收方式 |
| --- | --- | --- |
| O1 手感可信 | 输入到动作 p95 ≤ 16.7ms；非法状态 0 次；换道 120ms ± 20ms | 录屏逐帧 + 自动化输入回放 |
| O2 关卡公平 | 10 万次组合模拟无解率 0；连续双轨障碍 0；新手保护区（前 3 块地）不出现双轨障碍且至少留 2 条安全轨 | Python 离线跑批报告 |
| O3 留存 | 次日回访 ≥ 25%；平均单局 ≥ 90s；重开率 ≥ 60% | 本地埋点导出 |
| O4 可维护 | 手感参数 100% 在 GameConfig；改数值不改代码；新增地块 ≤ 30 分钟 | 代码走查 + 实操计时 |

### 2.2　非目标

| 不做 | 为什么 | 什么时候再考虑 |
| --- | --- | --- |
| 联网 / 排行榜 | 引入服务器成本与作弊问题，与单机交付冲突 | V2 之后，且有真实用户时 |
| 内购 / 广告 | 没有商业化诉求，广告会毁掉“3 秒重开” | 不做 |
| 二段跳 / 翻滚 / 技能 | 每个都增加状态组合与调参成本 | V1.1 观察玩家是否真的想要 |
| 弯道 / 斜坡 / 隧道 | 需要重做相机与轨道系统 | V2 |
| 每日任务 / 签到 | 没有用户基数时是空转 | 有 1000 DAU 再说 |
| 云存档 | 无服务器 | 不做 |

### 2.3　取舍原则

当范围与质量冲突时，按这个顺序砍：皮肤 → 道具 → 音效 → 归因提示。核心的“跑、跳、滑、换道、地块公平、存档”永不砍。

## 3　用户与场景

### 3.1　两类用户，两种成功

一类决定留存，一类决定传播。V1 只优化第一类，但界面与文档要为第二类服务——因为这是你作为独立开发者的作品集。

### 3.2　Persona A：碎片时间玩家（主）

| 维度 | 描述 |
| --- | --- |
| 画像 | 28 岁，通勤族，地铁上单手操作，静音，注意力随时被打断 |
| 目标 | 三分钟内获得“我做得好”的正反馈，而不是被教育 |
| 痛点 | 教程、加载、广告、死亡原因不明、重开要等 |
| 成功时刻 | 第三次尝试跑到 400m，比上次远；或者第一次解锁新皮肤 |
| 设计含义 | 零教程、零加载、单手可玩、死亡即归因、3 秒重开 |

### 3.3　Persona B：作品集访客（次）

| 维度 | 描述 |
| --- | --- |
| 画像 | 招聘者或同行，从 GitHub / 小红书点进来，30 秒决定要不要细看 |
| 目标 | 判断“这个人能不能独立把一个东西做完” |
| 痛点 | README 只有截图、跑不起来、代码没有结构 |
| 成功时刻 | 点开网页版 5 秒内能玩，且手感不糊弄 |
| 设计含义 | Web 试玩版、README 三段式、30 秒演示 GIF |

### 3.4　JTBD（待办任务）

- 当我只有几分钟且只有一只手时，我想立刻进入一个能赢的挑战，这样我能立刻获得掌控感。
- 当我失败时，我想马上知道为什么，这样我不会觉得是游戏在耍我。
- 当我想证明自己变强时，我想看到可比较的成绩（历史最高、里程碑），这样我有理由再来一局。

### 3.5　关键场景走查

| 时刻 | 用户状态 | 系统应该做什么 | 失败信号 |
| --- | --- | --- | --- |
| 首启 0–30s | 怀疑、不想读字 | 直接进对局，前 3 块地教跳/滑 | 出现教程弹窗、加载超过 3s |
| 单局 30–90s | 进入心流 | 节奏稳定上升，视觉反馈清晰 | 突然加速、障碍被遮挡 |
| 死亡瞬间 | 挫败 | 0.3s 慢动作 + 撞击点高亮 + 一句话归因 | 黑屏、无解释、强制看广告 |
| 结算 | 想再来 | 3 秒内可重开，显示最高分差距 | 必须回主菜单 |
| 次日回访 | 犹豫 | 主菜单直接显示“距最高分还差 XXm” | 空荡的主菜单 |

## 4　竞品与差异化

### 4.1　横向对比

| 维度 | 地铁跑酷 | 神庙逃亡 | Chrome Dino | 本作 |

| 上手成本 | 低（但教程长） | 低 | 零 | 零 |

| 内容量 | 极大 | 大 | 极小 | 小（程序化） |
| 商业化 | 重 | 重 | 无 | 无 |
| 本作差异点 | — | — | — | 确定性与可解释性，而非内容量 |

### 4.2　定位一句话

“不是更好玩的跑酷，而是更讲道理的跑酷。”

### 4.3　差异化如何被感知

- 开局 3 秒进游戏（对比：主流产品 10 秒以上的加载与登录）。
- 死亡归因（对比：几乎没有竞品告诉你为什么死）。
- 稳定的单局长度（对比：地铁跑酷越跑越长，碎片时间接不住）。

## 5　核心体验设计

### 5.1　核心循环

| 环节 | 玩家在做什么 | 系统在做什么 | 心理学目标 |
| --- | --- | --- | --- |
| 跑 | 观察前方 | 匀速推进，保证视野 | 建立节奏 |
| 读 | 识别障碍类型 | 障碍用形状/颜色区分跳与滑 | 可读性 |
| 决 | 跳 / 滑 / 换道 | 即时反馈，无输入延迟 | 掌控感 |
| 赏 | 吃金币、听音效 | 连击递增，音效递进 | 即时奖励 |
| 败 | 撞上 | 慢动作 + 归因 | 服气 |
| 再来 | 点一下 | 3 秒内回到跑动 | 低成本重试 |

### 5.2　单局节奏（定性）

本表只描述每个阶段的意图，不承载数值；速度、权重、密度一律以 5.3 的公式与表为准，避免两处数字打架。

| 阶段 | 距离参考 | 玩家在做什么 | 设计意图 |
| --- | --- | --- | --- |
| 开局 | 0–90 m | 学跳、学滑，还不需要选路 | 先赢一次，建立信心 |
| 建立 | 90–400 m | 三种动作开始组合，偶尔换道 | 形成肌肉记忆 |
| 压力 | 400–900 m | 连续决策，双轨障碍开始出现 | 进入心流 |
| 高手 | 900–1500 m | 提前规划路线、攒金币连击 | 技巧有回报 |
| 极限 | 1500 m+ | 只有最稳的路线能过 | 天花板可见，但不封死 |

### 5.3　难度模型（唯一权威）

本节是速度与权重的唯一权威来源。文档别处出现的任何速度、密度数值，都必须由这里计算得出；两者冲突时以本节为准。

速度曲线：v(d) = v₀ + (v_max − v₀) × (1 − e^(−d/λ))，其中 v₀ = 12 m/s，v_max = 26 m/s，λ = 600 m。

说明：26 m/s 是渐近上限而非可达到的硬阈值——d = 1500 m 时约 24.9 m/s，d = 2000 m 时约 25.5 m/s，之后增速趋缓。

| 距离 d | 速度 v(d) | 双轨障碍权重 | 玩家感受 |
| --- | --- | --- | --- |
| 0 m | 12.0 m/s | 0% | 教学区 |
| 100 m | 14.2 m/s | 0% | 开始有压力 |
| 250 m | 16.8 m/s | 6% | 节奏建立 |
| 500 m | 19.9 m/s | 14% | 必须预判 |
| 750 m | 22.0 m/s | 20% | 高手区入口 |
| 1000 m | 23.4 m/s | 24% | 稳定高压 |
| 1500 m | 24.9 m/s | 30%（封顶） | 极限 |
| 2000 m+ | → 26 m/s（渐近） | 30%（封顶） | 不再变难 |

地块权重：安全块从 0.45 线性降到 0.08；双轨障碍从 0 线性升到 0.30，在 1500 m 处封顶。

硬约束：任意连续两块地不得同为双轨障碍；任意地块不得三轨全封；道具只出现在安全轨道。

### 5.4　首分钟体验（不弹教程）

新手保护区（前 3 块地，约 0–90 m）的规则：不使用双轨障碍；每块地至少保留 2 条安全轨；判定窗口放宽到 1.5 倍。也就是说“保护”指的是不会死得莫名其妙，而不是没有障碍可学。

- 第 1 块地：纯金币，让玩家先吃到。
- 第 2 块地：单轨低障碍，宽度放宽，教跳；跳跃音效配合。
- 第 3 块地：单轨横杆，高度放宽，教滑；滑铲音效配合。
- 第 4 块地起：退出保护区，按 5.3 的权重正常生成。
原则：用关卡教，不用弹窗教。任何教程弹窗都会打断“我先玩一把”的冲动。

### 5.5　失败设计

| 环节 | 做法 | 目的 |
| --- | --- | --- |
| 死亡瞬间 | timeScale 0.25，持续 0.35s | 给大脑一个“我看到了”的缓冲 |
| 撞击点 | 高亮 1.5s，红色描边 | 明确指出是哪一下 |
| 归因 | 三种文案：起跳过早/过晚、未滑铲、换道时机不对 | 把“我运气不好”变成“我下次能改” |
| 重开 | 结算页 3 秒倒计时后可直接点任意处开始 | 把重试成本压到最低 |

### 6.3　P0 关键需求的验收标准

#### R-01 / R-02　输入层

- 规则：所有输入（键盘、触屏）先进入 InputManager，再分发为五类指令；原始输入不直接驱动角色。
- 验收：连续快速点击跳跃，角色只起跳一次；滑动方向误判率 < 2%；换道指令在冷却期内被丢弃且不排队。

#### R-03 / R-04　角色状态机

| 当前状态 | 允许的输入 | 结果 | 验收 |
| --- | --- | --- | --- |
| Run | Jump / Slide / Left / Right / UseItem | 进入对应状态；UseItem 不改变主状态 | 无延迟，动画与位移同步 |
| JumpUp / JumpDown | Left / Right / UseItem | 换道；跳跃与滑铲被丢弃 | 空中按跳跃无任何反馈 |
| Slide | Left / Right / UseItem | 换道；跳跃被丢弃 | 滑铲期间按跳跃无效 |
| SwitchLane | 全部丢弃 | 保持当前状态直到插值结束 | 快速连按不会抖动 |
| Hit | 全部丢弃 | HitStunDuration 后回到 Run | 受击时长读配置，改配置不改代码 |
| Death | 全部丢弃 | 全部冻结 | 死亡后分数不再变化 |

Hit 的进入条件：碰撞障碍且持有护盾（消耗一层）→ Hit；无护盾 → Death。受击时长统一读 GameConfig.HitStunDuration（默认 0.30s），不做硬编码。

#### R-10　道具与 UseItem

- 规则：拾取入包不再自动生效；玩家点道具栏消耗，UseItem 只在 Run / JumpUp / JumpDown / Slide 下被接受，且不改变主状态、不打断位移。
- 在 SwitchLane / Hit / Death 下，UseItem 一律丢弃，不排队、不延后执行。
- 验收：连续点击道具栏只消耗 1 个；换道过程中点击无效且不吞掉下一次点击；死亡后再点不会触发任何效果。

#### R-06 / R-07　地块生成

- 规则：地块长度统一，池化复用；每次生成前做一次“可通行性”校验。
- 验收：跑 1500m 后内存波动 < 10%；不出现三轨同时封锁的地块；不出现连续两块双轨障碍。

#### R-12　存档

- 规则：写入采用“临时文件 + 改名”的原子操作，避免写一半崩溃。
- 验收：强制杀进程后重开，金币与最高分不丢失；手动损坏 Json 后启动，游戏正常进入且生成默认存档。

### 6.4　P1 / P2 的范围说明

P1 是“可发布但体验残缺”的部分，优先补：相机与撞击反馈 → 死亡归因 → 设置 → 皮肤商店。

P2 只在 V1 发布后、有真实反馈时再做，避免在无人使用的功能上烧时间。

## 8　度量与埋点

### 8.1　北极星指标

单局有效游玩时长（中位数）。理由：它同时反映手感、难度与留存意愿，且不依赖联网。

### 8.2　护栏指标

| 指标 | 警戒线 | 含义 |
| --- | --- | --- |
| 崩溃率 | > 0.5% | 工程质量出问题 |
| 首局 60s 完成率 | < 50% | 难度或教学有问题 |
| 重开率 | < 40% | 失败设计让人不想再来 |
| 平均单局 | < 60s | 节奏太短或太难 |

### 8.3　埋点事件

| 事件 | 触发时机 | 关键字段 |
| --- | --- | --- |
| session_start | 启动 | session_id, version, device, tier |

### 8.4　单机产品的度量局限（必须承认）

没有服务器就没有聚合数据，也就没有 A/B 实验能力。V1 的指标只能来自：① 本地 JSONL 日志；② 设置页的“导出诊断包”（用户自愿）。这意味着：所有结论都带样本偏差，只能做方向性判断，不能做统计显著性。

这是“零服务器”的代价，接受它，并把精力放在体感调优与离线验证上。

## 9　技术方案与约束

### 9.1　ADR-001：为什么仍然选 Unity

| 维度 | Unity | WebGL（three.js） |
| --- | --- | --- |
| 移动端性能 | 强（原生、成熟合批） | 中（受浏览器限制） |
| 分发摩擦 | 需下载安装 | 点开即玩 |

| 美术/动画管线 | 成熟（骨骼、状态机） | 需自建 |
| 触屏输入 | 成熟 | 需处理浏览器手势冲突 |
| 结论 | V1 主版本 | V1 试玩版（M3 追加，3 天） |

决策：主版本仍用 Unity，因为移动端帧率与输入稳定性优先；但用 three.js 做一个“三块地循环”的极简试玩页，挂在 GitHub Pages 上，作为分享链接与作品集入口。两者不共享代码，避免双端维护成本。

### 9.2　架构约定

| 模块 | 职责 | 边界（不该做什么） |
| --- | --- | --- |
| InputManager | 统一输入、防抖、冷却 | 不驱动角色，只发指令 |

### 9.3　用 Python 做关卡离线验证（结合你的技术栈）

Unity 里跑 10 万次关卡组合太慢，也没法在 CI 里跑。做法：把地块定义抽成纯数据（类型、安全轨道、障碍坐标），用 Python 复刻生成规则与玩家模型，做三件事：无解检测、密度统计、回归对比。

#### 完美玩家模型（必须先定义，跑批结果才可信）

“完美”不等于“全知”。V1 采用的模型是：看得见、反应得过来、但不会预知未来。参数如下，全部与 GameConfig 同源。

| 参数 | 符号 | 取值 | 来源 / 依据 |
| --- | --- | --- | --- |
| 反应时间 | Rt | 250 ms | 人类视觉—动作延迟中位数，休闲游戏常取 200–300ms |
| 决策粒度 | Δt | 16.7 ms | 60fps 一帧，逐帧模拟 |
| 前方视野 | Vf | 40 m | 16:9、FOV 60° 下屏幕上方可见距离 |
| 视野时长 | Tf = Vf / v(d) | 随速度变化 | 速度越快，看到障碍的窗口越短 |
| 跳跃判定窗口 | Wj | ±120 ms | 与手感参数一致，超出即判为无效输入 |
| 滑铲判定窗口 | Ws | ±120 ms | 同上 |
| 换道耗时 | Tl | 120 ms | GameConfig.LaneSwitchDuration |
| 受击硬直 | Th | 300 ms | GameConfig.HitStunDuration（仅护盾命中时有意义） |

#### 无解判定

| 判定 | 条件 | 说明 |
| --- | --- | --- |
| 可通过 | 存在一条策略序列，使每个障碍都至少有一个合法输入时刻 | 合法 = 输入时刻落在判定窗口内，且 ≥ 障碍进入视野时刻 + Rt |
| 来不及 | 障碍进入视野到撞击的时间 < Rt + W | 再快的反应也来不及，属于设计缺陷 |
| 无解 | 所有策略序列都至少出现一次“来不及”，或出现三轨同时封锁 | 此类组合占比即为无解率 |

跑批脚本必须读取与游戏同一份 GameConfig，禁止脚本内另存一套参数，否则结论不可迁移。

- 无解检测：按上述模型逐帧模拟，输出无解率与首个无解地块的坐标。
- 密度统计：每 100m 的障碍数量、双轨障碍占比，输出曲线，并与 5.3 的权威表核对。
- 回归测试：每次改权重表跑 1 万次，输出与上次的差异报告（新增无解、密度偏移）。
产出：一份 CSV + 一张难度曲线图，直接贴进版本评审。

### 9.4　配置化

GameConfig 至少覆盖：速度区间与 λ、换道时长、跳跃初速与重力、滑铲时长、受击硬直、跳跃/滑铲判定窗口、地块权重表、新手保护区长度、道具刷新概率、音效音量。任何手感调整都不应改代码。

| Pause → Playing | 点击“继续” | 恢复 BGM 与位移 |
| Playing → Dead | 角色进入 Death 状态 | 停止生成、停止计分、出结算 |
| Dead → Prepare | 结算页点“再来一局”或 3 秒后自动 | 重置本局数据，直接回到 Prepare，不回主菜单 |
| Dead → Menu | 结算页点“返回主页” | 保存结算数据后回主菜单 |

| 地块类型 | 安全轨道 | 权重（0 m → 1500 m） | 校验规则 |
